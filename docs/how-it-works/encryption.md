# Encryption and shards

Everything a drive holds is sealed on the Mac before it leaves: file content, file and folder names, modification times. The server stores sealed bytes under the SHA-256 of those bytes and a tree of nodes whose names and keys it cannot open. Content is cut into shards by content-defined chunking, so an edit uploads only the shards it touched, and within one drive identical content is stored once.

The format is version 1. Its full description is at the top of [`crypt.rs`](../../crates/ludy-proto/src/crypt.rs); this page is the summary. Nobody but its author has reviewed it; see [known problems](../known-issues.md#the-encryption-format).

## Keys

Every key is 32 bytes.

| Key | Belongs to | Made | What it does |
|---|---|---|---|
| Node key | One file or folder | At random | A folder's key wraps the keys of its children, so whoever holds a folder's key can read everything below it and nothing above or beside it |
| Root key | The drive's root folder | At random, when the drive is created | It is the node key everything hangs from. It is what the Mac's [keystore](engine.md#drives-and-keys) holds |
| Dedup key | One drive | At random; stored on the server wrapped by the root key | Makes a shard's key and the cut points a function of the content, so the same bytes written twice in a drive are stored once |
| Shard key | One shard | From the dedup key and the shard's plaintext | Encrypts that shard and nothing else. It is carried in the file's manifest |

The root key is stored on the server wrapped by itself. That gives nothing away and lets a client check that the key it holds is this drive's. Wrapping keys for people (public keys, sharing) is not designed.

## Shards

Content is cut with FastCDC (256 KiB minimum, about 2 MiB on average, 16 MiB maximum), so the cut points follow the bytes and an edit moves only the shards around it. The table that decides the cut points is derived from the drive's dedup key, so the lengths of a file's shards, which the server sees, are not a function of the content alone.

A shard's plaintext is split into frames of 64 KiB. Each frame is sealed with ChaCha20-Poly1305 under the shard key, with the frame's number as the nonce, and its 16-byte tag follows it. A sealed shard is the frames end to end, so any plaintext range maps to a ciphertext range and a reader fetches only the frames it needs.

A sealed shard is named by the SHA-256 of its sealed bytes. The server can check that without being able to read them, and refuses an upload whose bytes do not hash to its name.

## Names, manifests and details

These are small sealed boxes: a version byte, a random 12-byte nonce, and ChaCha20-Poly1305 with the node's id in the associated data, so a box moved to another node does not open.

| Box | Sealed under | Holds |
|---|---|---|
| Name | The node's own key | The name, Unicode NFC, padded to a multiple of 32 bytes |
| Wrapped key | The parent folder's key | The node's key |
| Manifest | The file's key | The version's size and its segments: each a shard (its name, length and key) or a range of generated bytes |
| Version details | The file's key | The modification time |

A folder cannot hold two children with the same name. The server enforces that without seeing names, on a hash keyed by the folder's key. Names are compared after NFC normalisation and are case-sensitive.

## What the server can see

No key reaches the server, so it cannot read content, names or modification times. What it does see has not been written down as a threat model. It includes: how many nodes a drive has and how they nest, the length of every sealed shard and which versions use it, a file's size as its writer stated it, when things change, and which files in a drive share shards.

## Synthetic files

A manifest segment can say "this many bytes of the generated stream for this seed" instead of naming a shard. A file made only of that stores a sealed manifest of under a kilobyte and nothing else, and reads like any other file: the reader generates the bytes. `ludy synth` makes one, and the demo script uses them for its 12 to 180 GB files, so that a drive far larger than the Mac's disk can be shown without anyone uploading 300 GB. Writing into such a file works: the written part becomes real shards and the rest stays generated.

They are for demos and tests. Nothing else in Ludy creates them.

## An upload, step by step

The engine's side of this is in [the engine](engine.md#writes); the requests are in [the server](server.md#the-protocol-is-the-boundary).

1. The engine cuts what changed and seals each new shard.
2. `POST /drives/:drive/missing` with the names of the sealed shards; the server answers which it lacks.
3. `PUT /drives/:drive/shards/:sha256` for those. The server checks each body against its name.
4. `PUT /drives/:drive/manifests/:sha256` with the sealed manifest.
5. `POST /drives/:drive/commit` with a `put` op naming the manifest and every shard the version uses. The server refuses it, saying what is missing, unless all of them are in storage.

A new small file is five requests: its create, then steps 2 to 5. Batching them is not built.

## What the format does not do

- Wrap a key for a person.
- Page a very large manifest: a manifest is one sealed blob, about 6 MB for a 180 GB file.
- Protect against a server that serves an older, genuine version of a file.
